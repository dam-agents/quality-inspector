# Quality-inspector profile creator

Writes the **product profile** quality-inspector needs to test one product: a directory
holding `profile.json` (how to run it, which builds exist, egress, boundary, settings),
`SKILL.md` (what a tester should know, user-facing only), `README.md` (for its
maintainers) and, only when no engine fits, `bin/` scripts. It usually lives in the
product's own repository, so the product team versions it with the product.

Paths below are relative to this skill's directory. Everything you write is in
**English**, whatever language the conversation is in.

## Ground rules

- **The contract is the core's.** `docs/profile-contract.md` of the quality-inspector
  definition is the one source of truth for every field and command, and each engine's
  configuration is in `engines/<name>/README.md` there. Read them in Phase 0; where this
  skill and the contract differ, the contract wins.
- **You may read the source; the profile must not leak it.** You work for the product
  team, so its charts, compose files, CI and docs are yours to read to learn how the
  product is deployed. The QA agent is black-box: whatever the profile says becomes what
  it knows. `SKILL.md` holds only what a user could tell
  ([references/tester-knowledge.md](references/tester-knowledge.md)); `profile.json`
  holds only what the nested install needs — never a copy of the chart's values or of the
  product's configuration reference.
- **Never inside a quality-inspector agent.** When `$HOME/.quality-inspector-onboarded`
  exists, stop: that agent must not author its own profile, and the profile is read-only
  to it. Tell the operator the product team writes or fixes it (an issue on the
  product's repository).
- **No secrets in the profile.** Passwords are generated by `bin/env init` into the
  instance's `credentials.env`. A private registry's credential is injected by the
  platform's gateway for that host — the profile names the host, never the credential.
- **The core stays product-agnostic.** Nothing here edits the quality-inspector
  definition. A missing engine or contract feature is a separate proposal to that
  repository; say so, never patch the core from here.
- **Confirm, don't guess.** Tag patterns, the sign-in bootstrap and the nested limits
  decide verdicts. Confirm each with the person or an observation (a registry listing, a
  trial install) and mark what stays unconfirmed in the brief.

## Workflow

Phases in order. Write no profile files before the person approves the Phase 1 brief.

### Phase 0 — Context

1. Guard: the sentinel above.
2. **Find the core** (the quality-inspector definition) and keep its path as `QI_CORE`:
   the `QI_CORE` environment variable; else this skill's real directory two levels up
   when it holds `docs/profile-contract.md` (the skill ships inside the definition);
   else ask for the definition's repository and `git clone --depth 1` it into a scratch
   directory. Read `docs/profile-contract.md`, list `engines/*/README.md`, note `VERSION`.
3. **Find the product and the profile's home.** Always `.quality-inspector/qi-profile-<product-slug>/`
   — the directory name is the skill name, and `.quality-inspector/` is the one directory of
   a repository the agent's egress opens, so a profile anywhere else cannot be installed.
   Default: the current repository. Ask when the working directory is not the product's
   repository, or when the profile belongs elsewhere (a product the team does not own → a
   separate profiles repository, same `.quality-inspector/` directory). No symlink or
   submodule in it (`docs/profile-contract.md` → Where it lives).
4. **An existing profile → update mode.** Read all of it, run the checker (Phase 4) to see
   where it stands, and change only what was asked. Keep `config` key names stable: an
   instance's `work/CONFIG.md` holds `profile.<key>` bullets, and a renamed key is unknown
   there — when a rename is unavoidable, the profile README says what instances change.

### Phase 1 — Discovery and the brief (approval gate)

Run [references/discovery.md](references/discovery.md): read the repository for the
deployment facts, confirm the build listing against the registry itself, and ask the
person what only they know (the sign-in bootstrap, the nested limits, which settings an
operator must choose). End with the **profile brief** — the table in that file, every row
filled or marked `unknown` — and get it confirmed.

### Phase 2 — How it runs

| The product ships as | Use | You write |
| --- | --- | --- |
| a Helm chart in an OCI registry | engine `helm-k3s` | `engine_config` only — no scripts |
| a chart, but its builds are listed where the engine cannot read them | `helm-k3s` plus own `bin/versions`, `bin/build-time` | the overriding commands only |
| anything else — a compose file, an image, a package, a binary | own `bin/` | [references/custom-bin.md](references/custom-bin.md) |

Check `$QI_CORE/engines/` for engines added since; each README says what it runs. When
own scripts would serve other products of the same shape too, tell the person it is a
candidate engine for the core (a separate change there), and still write the profile's
scripts now.

### Phase 3 — Write the files

Create the directory and fill each template. Resolve every `<fill: …>` and every
`TODO(profile)` line, or delete the part that does not apply — the checker fails on any
that remain.

| Template | Becomes | Notes |
| --- | --- | --- |
| `templates/profile.helm-k3s.json.template` or `templates/profile.custom.json.template` | `profile.json` | Fields: the contract; `engine_config`: the engine's README. |
| `templates/SKILL.md.template` | `SKILL.md` | [references/tester-knowledge.md](references/tester-knowledge.md). |
| `templates/README.md.template` | `README.md` | Delivery, channels, config, egress, diagnosis, keep-in-step rule. |
| `templates/bin/env.template`, `versions.template`, `build-time.template` | `bin/env`, `bin/versions`, `bin/build-time` | Own scripts only; `chmod +x`. |

- **`config` keys** are what an operator may need to change per instance: a chart or
  image repository, a prerequisite's version, an optional stand-in. Each gets a string
  `default` and one `about` sentence; `"ask": true` only for a value onboarding cannot
  default. What every instance shares stays literal in `engine_config` or the scripts.
- **`suite/`** only for files tests need that the core does not ship (upload fixtures, a
  helper, the security run's `lib/security-api.ts` — brief row 18). The core's suite
  skeleton wins on every path it already has, so never put tests, the sign-in setup or
  `e2e.config.ts` there.
- **`scenarios/`** — the product team's flows, one `<slug>.md` each, in the form of
  [profile-contract.md](../../docs/profile-contract.md) → `scenarios/`: a title, then
  `## AC-<k> — <name>` blocks with Given/When/Then in a user's words. Offer one golden-path
  scenario per main area from the brief; the team owns and extends them, and a PR that
  changes how an area works updates its scenario. The nightly run adopts each one.
- **Channels** are named in the README (operators choose them), build names in
  `SKILL.md` (testers read them in reports).

### Phase 4 — Validate

```bash
node scripts/check-profile.mjs --core "$QI_CORE" <profile-dir>
```

It checks the contract (manifest, commands, SKILL.md frontmatter, leftover template
markers, literal secrets, black-box hints, plain files only — no symlink or submodule)
and runs the engine's own offline check. Fix every `FAIL`; judge every `WARN` — fix it
or tell the person why it stays. Then the read-only live check, which lists builds from
the real registry (needs the network and `curl`, `jq`, `node`):

```bash
node scripts/check-profile.mjs --core "$QI_CORE" --live <profile-dir>
```

Show the person the candidate and baseline it found, with their publish times, and ask
whether those are the builds they expect — a tag regex that picks the wrong tag fails
silently otherwise. `--set <key>=<value>` checks a non-default setting;
`--candidate` / `--baseline <channel>` another channel pair.

The acting commands (`bin/env up`, `reset`) need the QA VM's runtime — usually root and
k3s. Run them only where the person says it is safe
([references/custom-bin.md](references/custom-bin.md) → Trying it out); otherwise the
agent's onboarding smoke test is their first real run — say so.

### Phase 5 — Hand-off

1. Commit on a branch of the product's repository and open a pull request the way that
   repository does; never push without asking.
2. Give the person the operator's steps, pointing at the core's `README.md` → Setup and
   → Black-box boundary instead of restating them:
   - add a skill source — this repository, `path` `.quality-inspector` — and assign the
     profile skill to the agent; the kit's egress already opens that directory, so the
     profile needs no rule of its own;
   - the egress rules that `scripts/egress-rules.sh` prints (`docs/black-box.md` → Egress
     rules) — every `egress` entry of `profile.json`;
   - a deny for every `boundary.urls` entry;
   - the `profile.<key>` values onboarding will ask for.
3. Say in three lines what the QA agent will treat as untestable (the "cannot do" list),
   so the first `not-testable` verdicts surprise nobody.
